## D-02. 채팅 모델: `gpt-4.1-mini`

| 항목 | 내용 |
|---|---|
| 근거 | `koreacentral` Global Standard 한도가 200이라 할당량 요청 없이 배포할 수 있습니다. 추론 모델이 아니어서 `temperature`로 답변 변동을 줄일 수 있고, 다른 리소스와 같은 지역에 둘 수 있습니다. |
| 제외한 대안 | `gpt-4o-mini`는 Global Standard 한도가 0이고, Standard는 2026-03-31에 종료되어 새로 배포할 수 없습니다(`ServiceModelDeprecated`). `gpt-5.4-mini`는 Global Standard 한도가 0입니다. `gpt-5-mini`는 한도가 500이지만 추론 모델이라 코드와 합격 기준을 다시 바꿔야 합니다. |
| 파라미터 | `max_completion_tokens=1000`, `temperature=0`. 답변 변동을 줄이려고 `temperature`를 0으로 고정합니다. 추론 모델 전용인 `reasoning_effort`는 보내지 않습니다. |
| 위험 | 수명 주기 상태가 `Legacy`이며 **2027-04-14에 퇴역**합니다. 답변이 1,000토큰에서 잘리면 JSON이 깨져 `MODEL_OUTPUT_INVALID`가 날 수 있습니다. |
| 배포 검증 | 2026-11-04 실제 배포에서 `temperature=0`과 JSON 스키마 응답이 동작했습니다. 임계치 검증의 모델 출력 오류 0건, 스모크 테스트 5/5, `AC-PERF-02`와 `AC-PERF-03` 통과입니다. 답변을 원문과 하나씩 대조하지는 않았고, p95 테스트는 합격 여부만 판정해 측정값이 남아 있지 않습니다. 검증 후 리소스는 삭제했습니다. |
| 재검토 조건 | 다시 배포할 때 응답이 잘리거나 p95 목표를 넘을 때, 또는 퇴역일이 실습 기간에 가까워질 때 |

강의 프롬프트의 "gpt 채팅 배포"에 맞춘 선택이며, 모델 이름은 환경 변수로 분리합니다. 할당량과 배포 유형별 종료일은 구독과 시점에 따라 달라지므로 배포 전에 runbook 2단계에서 확인합니다.

## D-03. 배포 유형: Global Standard

| 배포 유형 | `koreacentral` `gpt-4.1-mini` | `koreacentral` `text-embedding-3-small` |
|---|---|---|
| Global Standard | 가능, 한도 200 (**채택**) | 가능, 한도 1,000 (**채택**) |
| Data Zone Standard | 목록에 없음 | 목록에 있음 |
| Standard(Regional) | 목록에 없음 | 목록에 없음 |

한도는 1,000 TPM 단위입니다. 2026-11-04에 이 구독에서 `az cognitiveservices model list`와 `usage list`로 확인했으며, 구독이 바뀌면 달라질 수 있습니다. **할당량 한도가 있어도 배포 유형별 종료일(`deprecationDate`)이 지나면 새로 배포할 수 없으므로 둘 다 확인합니다.**

| 항목 | 내용 |
|---|---|
| 근거 | 두 모델을 `koreacentral`에서 지역 내 처리(Regional)로 배포할 수 없고, `gpt-4.1-mini`는 Data Zone도 목록에 없습니다. 실습 문서에 민감 정보가 없으므로 두 모델에 공통으로 쓸 수 있는 Global Standard를 택합니다. 모든 리소스를 `koreacentral`에 둡니다. |
| 대안 | `swedencentral` 등 다른 지역으로 Azure OpenAI를 옮기는 방법을 검토했으나, 그쪽의 `gpt-4o-mini` Standard는 이미 종료되어 배포할 수 없었습니다. |
| 위험 | 저장 데이터는 지정 지역에 있어도 추론은 다른 Azure 지역에서 처리될 수 있습니다. **업무 문서에 그대로 적용하면 안 되는 결정입니다.** |

## D-04. 검색 방식: 순수 벡터 검색

| 항목 | 내용 |
|---|---|
| 근거 | 요구사항이 벡터 검색입니다. 또한 임계치가 점수의 의미에 의존합니다. 문서에 따르면 벡터 검색의 cosine 점수는 0.333~1.00 범위의 유사도 기반 값이지만, 하이브리드 검색의 점수는 순위 기반 RRF 값이라 같은 임계치를 쓸 수 없습니다. |
| 대안 | 3주차에서 쓴 하이브리드와 교차 인코더는 글자 일치에 강하지만 호출 비용과 임계치 설계가 달라집니다. |
| 재검토 조건 | 고유명사, 제품 코드 질문에서 검색 실패가 반복될 때 |

점수 변환 공식입니다. Azure는 `@search.score = 1 / (1 + 코사인 거리)`로 정의합니다.

```text
코사인 유사도 = 2 - 1 / score
score        = 1 / (2 - 코사인 유사도)
```

## D-07. 임계치: `@search.score` 0.5735

2026-11-04에 `text-embedding-3-small`과 `gpt-4.1-mini`로 보정한 값입니다. `MIN_SEARCH_SCORE`로 앱에 반영했습니다. 처음의 잠정값 0.625(코사인 0.40)는 측정값이 아닌 시작값이었으며, `main.parameters.json`의 기본값으로 남아 있습니다. 4주차의 0.25나 3주차의 -3.18은 다른 모델의 다른 척도이므로 가져올 수 없습니다.

### 보정 결과

| 항목 | 값 |
|---|---|
| 임계치 | 0.5735 (코사인 0.2563) |
| 선정용 답 있는 질문 최저 점수 | 0.5816 |
| 선정용 주제 밖 질문 최고 점수 | 0.5654 |
| 분포 겹침 | 없음, 놓친 답 있는 질문 0개 |

| 검증 기준 (결과를 보기 전에 정함) | 목표 | 결과 |
|---|---|---|
| 주제 밖 차단 | 5/5 | 5/5 |
| 같은 주제 차단 | 3/3 | 3/3 |
| 답 있는 질문 답변 | 8/10 이상 | 9/10 |
| 모델 출력 오류 | 0건 | 0건 |

- **놓친 질문:** "연결된 기기는 어디에서 해제하나요?"는 점수 0.5668로 임계치에 걸렸습니다.
- **변별력의 한계:** 선정용 두 분포의 차이가 0.016뿐입니다. 검증에서 주제 밖 질문 "자전거 체인에 기름을 치는 방법은?"이 0.5751로 임계치를 넘었고, 임계치가 아닌 그다음 검사에서 차단됐습니다.
- **같은 주제 질문:** 검증 점수 0.60~0.62로 3개 모두 임계치를 넘었고, 그다음 검사에서 차단됐습니다.
- **확인 범위:** `answered`는 정답 여부까지 판정한 것이 아닙니다. 원문과 하나씩 대조하지 않았습니다. 운영자 계정으로 로컬에서 실행한 결과이며, 원본은 `calibration_result.json`입니다.
- **재보정 조건:** 임베딩 모델이나 문서를 바꾸면 다시 보정합니다. 검증을 다시 하려면 새 검증 질문이 필요합니다.

점수 비교는 변환 오차가 없도록 `@search.score` 척도에서 합니다. 임계치와 같은 점수는 통과시킵니다(AC-NF-03).

### 보정 절차 (첫 배포의 인덱싱 후, 스모크 테스트 전)

답 없는 질문은 막는 장치가 다르므로 두 종류로 나눕니다.

| 질문 종류 | 예 | 막는 장치 |
|---|---|---|
| 주제 밖 (`off_topic`) | 김치찌개 끓이는 법 | 임계치 |
| 같은 주제, 답 없음 (`in_domain`) | 구름노트 대표 이름 | 모델 판단, 인용문 대조 |

1. 검색 점수를 보기 전에 질문을 정합니다. 선정용과 검증용을 별도로 구성하며, 각각 답 있는 질문 10개, 주제 밖 5개, 같은 주제 3개입니다.
2. 선정용 질문으로 최고 점수를 구합니다.
3. 주제 밖 질문의 최고 점수와 답 있는 질문의 최저 점수 사이 중간값을 임계치로 정합니다. 같은 주제 질문은 점수만 기록하고 임계치 계산에 넣지 않습니다.
4. 두 분포가 겹치면 주제 밖 질문을 모두 막는 값을 우선합니다. 놓치는 답 있는 질문의 수를 기록합니다.
5. 검증용 질문을 실제 답변 흐름 전체로 한 번만 평가합니다. **검증 결과를 본 뒤 값을 다시 조정하지 않습니다.** 조정이 필요하면 새 검증 질문을 만듭니다.
6. 값과 결과를 이 문서에 기록하고 `MIN_SEARCH_SCORE`로 설정합니다.

이 절차는 3주차에서 기준값 선정용과 검증용 질문을 분리한 방식을 따릅니다. 질문 수가 적으므로 결과는 이 문서 묶음에 대한 근거일 뿐 일반화할 수 없습니다. 비용은 검증의 채팅 호출을 포함해 약 $0.1 이하로 추정합니다. 강의 프롬프트의 4단계에는 없는 절차라 runbook에 추가합니다.

**규칙을 바꾼 이유:** 처음 규칙은 답 없는 질문을 모두 임계치로 막는 것이었습니다. 로컬 `bge-m3`로 실행하니 같은 주제 질문의 점수(최고 0.776)가 답 있는 질문(최저 0.668)보다 높아 임계치가 0.777이 됐고, 검증에서 답 있는 질문 10개가 모두 막혔습니다. 벡터 유사도는 주제가 비슷한지만 보므로 이 구분을 할 수 없습니다.

**바꾼 규칙의 로컬 확인:** 같은 `bge-m3`와 `llama3.2`에서 임계치는 0.6411이 됐고, 검증에서 답 있는 질문 9/10 답변, 주제 밖 5/5 차단, 같은 주제 3/3 차단, 모델 출력 오류 0건이었습니다. 절차가 동작한다는 확인일 뿐이며, 이 값은 Azure 모델에 쓸 수 없습니다.

## D-08. 환각 방지: 3중 검사

| 단계 | 막는 상황 | 실패 시 |
|---|---|---|
| 임계치 | 문서와 무관한 질문 | 모델 호출 없이 `not_found` |
| 모델의 `answerable` | 점수는 높지만 답은 없는 질문 | `not_found` |
| 인용문 원문 대조 | 근거에 없는 내용을 인용한 답변 | `not_found` |

| 항목 | 내용 |
|---|---|
| 근거 | 3주차에서 쓴 인용문 대조와 실패 시 답변하지 않는 원칙을 이어받습니다. 벡터 유사도는 주제가 비슷한지를 볼 뿐 답이 있는지는 보장하지 않으므로 임계치만으로는 부족합니다. |
| 출처 결정 | 출처는 모델이 적은 ID가 아니라 인용문이 실제로 들어 있는 근거 청크로 정합니다. 3단계에서 `llama3.2`가 답과 인용문은 맞게 쓰고 문서 ID만 서로 바꿔 적어 올바른 답이 `not_found`가 된 일이 있었습니다. 근거 후보에 아예 없는 ID는 여전히 `not_found`입니다. |
| 비용 | 정상 답변도 인용문이 맞지 않으면 `not_found`가 될 수 있습니다. 틀린 답보다 답하지 않는 쪽을 택한 결정입니다. |
| 한계 | 인용문이 맞아도 답변 문장이 잘못 해석했을 수 있습니다. 이는 실제 모델 평가로만 확인할 수 있습니다. |
| 제외 | 3주차의 "가까운 청크 추천"은 넣지 않습니다. 강의 범위 밖이고 `not_found`에 청크를 담으면 근거로 오해될 수 있습니다. |

## D-11. 인증: Managed Identity + API 키

| 항목 | 내용 |
|---|---|
| 서비스 간 | 키 없이 시스템 할당 Managed Identity와 RBAC를 사용합니다. 저장소에 유출될 키가 없습니다. |
| 호출자 | 공개 엔드포인트라 누구나 호출하면 모델 비용이 발생합니다. 그래서 `X-API-Key`를 받고 그 키를 Key Vault에 둡니다. **강의 프롬프트에 직접 명시되지는 않았으며, 비용 보호와 Key Vault의 쓰임을 위해 추가했습니다.** |
| 권한 최소화 | App은 AI Search `Search Index Data Reader`만 갖습니다. 인덱싱은 운영자 계정으로 합니다. |
| 위험 | Managed Identity의 새 권한은 적용까지 몇 시간 걸릴 수 있다고 문서에 나와 있습니다. 배포 직후의 401/403은 runbook에서 이 경우를 먼저 확인합니다. |
| 키 생성 | 운영자가 임의 값을 만들어 `azd env set APP_API_KEY`로 설정하면 보안 파라미터로 Key Vault에 저장됩니다. 재배포해도 값이 바뀌지 않아 호출자를 다시 설정할 필요가 없습니다. 32자 미만이면 배포가 실패합니다. 값은 `.azure/`에 평문으로 남으므로 저장소에서 제외합니다. |

## D-12. 로컬 폴백: Ollama

| 항목 | 내용 |
|---|---|
| 결정 | `LLM_PROVIDER=ollama`에서 채팅 `llama3.2`, 임베딩 `bge-m3`, 메모리 내 벡터 저장소를 씁니다. |

| 사전 작업 | `ollama pull bge-m3`로 내려받습니다. 3단계에서 내려받았고 1024차원을 확인했습니다. |
| 한계 | 이 PC는 CPU 전용이라 느리고(`llama3.2` 호출당 약 13~30초), 품질과 성능의 근거가 되지 않습니다. AC-PERF는 이 모드에 적용하지 않습니다. 임계치도 별도로 정해야 합니다. |

## D-14. 성능 목표

| 항목 | 내용 |
|---|---|
| 목표 | `answered` p95 8초 이하, `not_found` p95 3초 이하 |
| 근거 | **측정값이 아닌 초기 목표입니다.** 임베딩과 검색 1초 안팎, 채팅 몇 초로 가정했고, `not_found`는 채팅을 부르지 않아 더 짧습니다. |
| 측정 한계 | 표본 20회의 p95는 사실상 두 번째로 느린 값(최근접 순위 19번째)이라 흔들림이 큽니다. 실습 판정용이며 운영 SLO의 근거로 쓰지 않습니다. |
| 재검토 조건 | 4단계 측정 후 원인을 확인합니다. 목표를 바꾸면 측정값과 이유를 이 문서에 남깁니다. |
